# Claude Code Prompt: BW Ordering System — Admin and Store Access

## Project Overview

Enhance the existing ordering system for BW by implementing role-based access for **Admin** and **Store** users.

The system must allow administrators to manage stores, cancel Transfer Requests (TR), adjust order submission deadlines, and view consolidated order items across all stores. Store users must be able to submit orders for BW products and warehouse items.

Before making changes, inspect the entire existing project, including:
- Frontend framework, UI components, and current page structure.
- Backend framework, API endpoints, and business logic.
- Database schema, models, migrations, and relationships.
- Existing authentication, authorization, and user roles.
- Current order, TR, store, product, and warehouse workflows.
- Existing validation, notifications, and error-handling patterns.

Use the existing technology stack and coding conventions. Do not rebuild the application from scratch, duplicate existing functionality, or remove working features.

If a required feature already exists, extend it instead of creating a separate implementation.

---

# PART 1: ROLE-BASED ACCESS CONTROL

Implement two primary user roles:

1. **Admin**
2. **Store**

### Admin permissions

Administrators must be able to:
- Manage stores.
- Cancel orders/TRs.
- Configure order submission deadlines.
- View orders from all stores.
- Filter consolidated order items by date.
- View order details, including store, products, quantities, and status.

### Store permissions

Store users must be able to:
- Log in to their assigned store account.
- View available BW products.
- View available warehouse items.
- Create and submit orders.
- View their own store's orders and order history.
- View order statuses and submission deadlines.
- Edit or cancel their own orders only when permitted by the existing business rules and order status.

### Security requirements

- Enforce role-based permissions on both the frontend and backend.
- Do not rely on hiding buttons or pages as the only access control.
- Store accounts must only access orders belonging to their assigned store.
- Admin-only APIs and actions must reject unauthorized store users.
- Validate all incoming requests on the backend.

# PART 2: ADMIN — CANCEL ORDER (TR)

Allow administrators to cancel any eligible Transfer Request (TR) or order.

### Requirements

1. Add a **Cancel Order** action to the appropriate admin order management page.
2. Display a confirmation dialog before cancellation.
3. Show relevant order information in the confirmation dialog:
   - TR/order reference number.
   - Store name.
   - Order date.
   - Order status.
4. Require a cancellation reason.
5. Update the order status to `Cancelled`, following the existing status conventions if they differ.
6. Record the administrator who performed the cancellation.
7. Record the cancellation timestamp and reason.
8. Display the updated status immediately after successful cancellation.
9. Prevent repeated or invalid cancellations.
10. Ensure cancellation does not silently delete the original order or its items.

### Business logic

- Determine which order statuses are eligible for cancellation.
- Prevent cancellation of completed, fulfilled, or otherwise locked orders unless the existing business rules explicitly allow it.
- If an order has already been processed by the warehouse, handle the cancellation according to the existing inventory and fulfillment logic.
- Do not automatically restore inventory or reverse stock movements unless the existing workflow requires it.
- Preserve a complete audit trail.

Provide appropriate success messages and clear error messages if cancellation fails.

# PART 4: ADMIN — CONFIGURABLE ORDER SUBMISSION DEADLINE

## Business requirement

The normal order submission deadline is **4:00 PM**. However, certain stores need additional time to post or submit their orders.

Administrators must be able to adjust the submission deadline instead of being restricted to a fixed 4:00 PM cutoff.

### Admin settings page

Create an **Order Submission Settings** section in the admin dashboard.

Provide the following capabilities:

1. Configure the default daily submission deadline, initially set to 4:00 PM.
2. Set a different deadline for a specific store.
3. Configure a deadline for a particular date when needed.
4. Allow an administrator to update an existing deadline.
5. Display the current effective deadline for each store.
6. Provide a way to reset a store-specific deadline to the default.
7. Display the date and time of the most recent deadline change and the administrator responsible.

### Deadline priority

Implement the following priority rules:

1. A date-specific deadline for the store takes priority.
2. Otherwise, a store-specific recurring deadline takes priority.
3. Otherwise, use the system-wide default deadline.

If the existing business process requires a different priority, document it and follow the established workflow.

### Store ordering behavior

- Show the effective submission deadline clearly on the store ordering page.
- Initially, all stores should follow the default 4:00 PM deadline unless configured otherwise.
- A store with an extended deadline must be able to submit orders until its applicable cutoff.
- Stores whose deadlines have passed must not be able to submit new orders for that deadline period.
- Display a clear message when a deadline has passed.
- Use the server's configured business timezone consistently. Make the timezone configurable if the application operates across multiple timezones.
- Enforce the deadline on the backend, not just through frontend validation.
- Prevent race conditions around the submission cutoff.
- If an order is already submitted, do not invalidate it simply because the deadline later changes.

### Deadline change history

Record:
- Previous deadline.
- New deadline.
- Applicable store or global setting.
- Effective date, if applicable.
- Administrator who made the change.
- Timestamp of the change.

Important: Do not hardcode 4:00 PM into the frontend or backend submission logic. Store the default deadline in the database or existing settings mechanism so it can be changed without modifying application code.

# PART 5: ADMIN — CONSOLIDATED STORE ORDER ITEMS WITH DATE FILTER

Create a dedicated admin page named **All Store Orders** or **Consolidated Orders**.

The purpose is to allow the administrator to see the items ordered by all stores for a selected date or date range.

### Date filter

Provide:
- Start date.
- End date.
- Apply Filter button.
- Reset Filter button.
- Optional quick filters such as Today, Yesterday, and This Week.

Use the actual order submission date or the relevant business date defined by the existing workflow. Make the date basis clear to the user.

### Consolidated order table

Display the following information where available:

- Order date.
- TR/order reference number.
- Store code.
- Store name.
- Product code or SKU.
- Product name.
- Product category.
- Item type: BW Product or Warehouse Item.
- Quantity ordered.
- Unit of measure.
- Order status.
- Submission timestamp.

If an order contains multiple items, display each item as a separate row or use an expandable order grouping that provides the same level of detail.

### Summary information

Above the table, display useful summaries such as:

- Total number of stores that submitted orders.
- Total number of orders/TRs.
- Total distinct products ordered.
- Total quantities ordered, grouped by product and unit of measure where appropriate.
- Number of pending, submitted, processed, and cancelled orders.

Do not add together quantities with incompatible units. For example, cases and individual pieces must remain distinguishable unless a valid conversion exists.

### Search and filtering

Allow administrators to:
- Filter by date or date range.
- Filter by store.
- Filter by order status.
- Filter by item type.
- Search by TR/order reference number.
- Search by product name or SKU.
- Sort table columns.
- Navigate through paginated results.

All filters must work together correctly.

### Product-level consolidated view

In addition to the detailed order list, provide an optional product summary view that groups ordered quantities across stores.

Example:

| SKU | Product | Item Type | Store A | Store B | Store C | Total |
|---|---|---|---:|---:|---:|---:|
| BW001 | Sample BW Product | BW Product | 10 | 15 | 8 | 33 |
| WH001 | Sample Warehouse Item | Warehouse Item | 5 | 3 | 7 | 15 |

The data above is illustrative only. Use actual database records and dynamically generate the store columns or an equivalent readable layout.

Ensure the totals are calculated from the filtered dataset and follow the application's quantity and unit-of-measure rules.

### Export

If practical within the existing stack, allow administrators to export the filtered results to CSV or Excel.

Exports must respect the same filters and authorization rules as the page.

# PART 6: STORE — ORDER BW PRODUCTS AND WAREHOUSE ITEMS

Allow store users to order two categories of items:

1. **BW Products**
2. **Warehouse Items**

Inspect the existing product and inventory models before implementing this feature. Reuse the existing catalog and stock data whenever possible.

### Store ordering page

Create an intuitive ordering interface with:
- BW Products category.
- Warehouse Items category.
- Product search.
- SKU/product code display.
- Product name and description.
- Unit of measure.
- Availability or stock information where appropriate.
- Quantity input.
- Add to Cart action.
- Cart summary.
- Remove item and update quantity actions.
- Order total quantities.
- Submit Order button.

Do not assume both item categories share the same inventory source. If they are stored in different tables or systems, preserve their respective inventory logic while presenting a unified ordering experience.

### Cart behavior

- Allow multiple products in one order.
- Prevent duplicate cart lines for the same product and item type unless the existing business rules require otherwise.
- Validate that quantities are positive and within allowed limits.
- Validate product availability and ordering restrictions.
- Display validation errors clearly.
- Revalidate product availability and the submission deadline when the order is submitted.
- Do not trust quantities, prices, product IDs, or store IDs supplied by the frontend without server-side validation.

### Order submission

When a store submits an order:

1. Verify that the authenticated user belongs to an active store.
2. Verify that the applicable submission deadline has not passed.
3. Validate all order items.
4. Generate a unique TR/order reference using the existing numbering convention.
5. Save the order header and all order items transactionally.
6. Associate the order with the authenticated user's store.
7. Record the submission timestamp.
8. Set the correct initial order status.
9. Display a confirmation page with the TR/order reference number.
10. Make the submitted order visible in the store's order history and the admin's consolidated orders page.

If submission fails, roll back the transaction so partial orders are not created.

### Store order history

Create a page where store users can view:
- TR/order reference.
- Submission date.
- Ordered items.
- Quantities.
- Status.
- Relevant deadline information.
- Cancellation information when applicable.

Store users must not be able to view other stores' orders or the complete consolidated order list.
